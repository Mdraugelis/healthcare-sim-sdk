# The science of simulating healthcare AI

A [Kindle EPUB edition](ebook/healthcare-simulation-sdk-textbook.epub) is also
available, with [transfer instructions](ebook/README.md). Its interactive labs
are adapted into static worked examples.

Open [index.html](index.html) in a browser. The book contains sixteen chapters,
eight interactive teaching labs, forty-seven rendered equations, worked
exercises, primary references, and numbered excerpts from the actual project.
It is an author draft designed for peer review; external scientific review and
institution-specific clinical validation remain pending.

The HTML embeds its styling, scripts, diagrams, equations and source excerpts.
It needs no server, CDN, account or internet connection to read or use the labs.
External bibliography links need a connection. Links to complete repository
files and QA records need the companion directory tree. Without JavaScript,
the chapters, equations, worked examples and native disclosures remain readable;
the calculators, search and review-note controls do not run.

## Reading and review

- Clinical and operational path: chapters 01 → 08 → 12 → 16.
- Quantitative path: chapters 02–05, then 09–11.
- Engineering path: chapters 07 and 13–16.
- Start an audit with the [source manifest](source_manifest.json) and
  [quality report](qa/quality_report.md).

Review notes are local to the browser. **Save before changing chapters or
exporting.** “Export saved JSON” preserves each saved note's reviewer, status,
timestamp and manuscript identity. Export does not renew old evidence. Saving
an older note explicitly renews it against the current manuscript and retains
its previous identity. “Reviewed” requires a name but is self-reported, not an
authenticated signature, a shared approval system or a clinical certification.
Browser storage can be unavailable or cleared; export a durable copy. In a
storage failure, Save retains a note in memory for export during that session.

## Authoring and rebuilding

Editable sources are `chapters/*.json`, `assets/style.css`, `assets/app.js` and
`build.py`. Run from the repository root with the project environment:

```bash
.venv/bin/python docs/textbook/build.py
```

The build requires Python with `mistune`, `matplotlib` and `beautifulsoup4`.
Versions used for this edition are recorded in the manifest. It reads local
source only and does not run a simulation or contact an external service.
`index.html` is generated: edit its source files and rebuild instead of editing
the generated HTML. The source manifest binds the baseline commit, working-tree
file hashes, chapter inputs, visual code, build script and build dependencies.
The baseline revision alone does not identify the local implementation.

Each chapter JSON supplies its title, objectives, prerequisites, Markdown body,
references, code references, review questions and exercise answers. A code
reference names a repository-relative file and optionally an exact qualified
Python symbol. The build resolves its actual AST line span, hashes the full
file, and embeds at most the first seventy lines. Longer excerpts are explicitly
labeled as selected opening excerpts, with the full referenced span shown.
This is traceability, not exhaustive code-path coverage.

Use fenced `math` blocks with one Matplotlib-compatible expression per block.
The build embeds vector equations and an expandable, escaped LaTeX source.
It fails on missing source symbols, duplicate HTML/SVG IDs, broken internal
anchors and changed dated evidence when a recorded artifact is locally present.
Chapter HTML is trusted author input; this builder is not an untrusted-document
sanitizer.

Chapter 12 cites dated synthetic results from ignored `outputs/`. Their hashes
are retained in the chapter and manifest; raw generated experiment output is
not copied into this book's source tree. If those files are absent, the dated
narrative and recorded hashes remain available, while direct artifact links
require recreation or an archival copy. The public demonstration can be
recreated with:

```bash
.venv/bin/python -m healthcare_sim_sdk.scenarios.malnutrition_prioritization.run_review_demo
```

If regenerated bytes differ, investigate the source, configuration and result
differences before updating the chapter's evidence hashes. Do not replace them
merely to suppress a build error. This documentation does not renew the
original malnutrition efficacy, financial or full equity claims.

## Reproduce documentation checks

The numerical checker executes the actual JavaScript math functions through
Node, then compares them with independent Python/SciPy/NumPy calculations and
selected SDK helpers. It does not start the full production regression suite.

```bash
.venv/bin/python docs/textbook/qa/check_numerics.py
```

Use `--node /absolute/path/to/node` if Node is not found. The checker records
its own hash, the current script hash, numerical environment and individual
results in `qa/numerical_results.json`.

The browser checker requires Node, Playwright and an installed Chromium/Chrome.
Use an existing environment with those dependencies. For example:

```bash
node docs/textbook/qa/check_browser.cjs
```

`NODE_PATH` can point to an existing Node dependency directory. `CHROME_BIN`
can specify an installed Chrome executable; otherwise Playwright uses its
configured Chromium. `PLAYWRIGHT_MODULE` can specify the Playwright module
path. The checker launches an isolated temporary browser profile against the
local file, uses no personal browsing session, and records the actual HTML hash
in `qa/browser_results.json`. It exercises all slider endpoints, search,
mobile navigation, saved review identities, export, printing, no-JavaScript
reading and horizontal reflow. It saves representative PNGs alongside results.

The [quality report](qa/quality_report.md) records what was actually checked,
including limitations. These checks are not a formal accessibility audit or
external scientific peer review. Rebuild first; then rerun checks when the
artifact or supporting numerical code changes. Do not claim prior QA applies
to a different HTML/script identity.

## Maintenance after project changes

1. Identify chapters citing any changed source file using the manifest.
2. Review the narrative against the new implementation, including units,
   timing, failure cases, assumptions and evidence applicability.
3. Recalculate affected examples independently and revise affected exercises.
4. Rebuild and rerun relevant documentation checks. Inspect representative
   desktop/mobile renders and changed equations or charts.
5. Update the quality report and preserve unresolved review questions.

Production test evidence remains in the project’s existing implementation
records. This documentation task does not turn selective prior regression
results into a newly executed full-suite run.
